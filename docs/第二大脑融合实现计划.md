# 第二大脑融合实现计划

> 超级大脑 × 古籍知识库 → 统一检索记忆引擎 → 接入 DGX Spark 的 OpenClaw
> 日期：2026-11-10 | 状态：待确认连接信息后进入实施

## 一、现状与目标对齐

已确认的现状：

| 项 | 现状 |
|---|---|
| 硬件 | NVIDIA DGX Spark（GB10，128GB 统一内存），局域网内可 SSH 访问 |
| 推理框架 | vLLM，OpenAI 兼容接口（模型名待确认，你提到「千问 3.8-27B」） |
| 两个系统 | 「超级大脑」「古籍」**目前主要是数据**，系统代码尚未成型 |
| 目标载体 | 作为 DGX 上 **OpenClaw** 的一部分 |

OpenClaw 是什么（已核实）：本地优先的开源 AI agent 框架（Node.js，前身 Clawdbot/Moltbot）。自带：多渠道消息入口（Telegram/飞书/企微等）、工具执行（Browser/Exec/Web）、自动化（Cron/Webhooks）、**记忆能力**、以及 **Skills 扩展生态**（ClawHub）。NVIDIA 官方有 DGX Spark 部署教程。

**目标**：把「古籍知识库」+「超级大脑记忆」融合成一个「极致向量化 + 人脑式思考」的第二大脑，作为 OpenClaw 的一个能力模块，精准辅助你。

## 二、总体架构

融合的关键动作：**抽出一个独立的「检索记忆引擎」，统一服务古籍知识库和超级大脑记忆，再以 skill 形式挂进 OpenClaw。**

```
┌─────────────────────────────────────────────────────────────┐
│  OpenClaw Gateway（已存在）                                    │
│    └─ Skill: second-brain（本次新增）                          │
│         └─ 封装为 agent 可调用的工具：search / remember / ask  │
└──────────────────────────┬──────────────────────────────────┘
                           │ HTTP 调用（本机 localhost）
┌──────────────────────────▼──────────────────────────────────┐
│  检索记忆引擎（本次新增，FastAPI 服务，跑在 DGX 上）              │
│    ├─ 混合检索：稠密(BGE-M3) + 稀疏(BM25) + rerank            │
│    ├─ 多粒度索引：条文级 / 段落级 / 篇章语义摘要级               │
│    ├─ 查询改写：中医术语归一、query expansion                 │
│    └─ 分层记忆：工作记忆 / 长期知识 / 情景记忆                 │
└──────────────────────────┬──────────────────────────────────┘
                           │
┌──────────────────────────▼──────────────────────────────────┐
│  推理层：vLLM 千问 27B（OpenAI 兼容 /v1/chat/completions）     │
│  向量模型：BGE-M3（embedding）+ BGE-reranker（精排）           │
│  向量库：Qdrant（本机 Docker 或二进制）                        │
└─────────────────────────────────────────────────────────────┘
```

分层职责清晰，任一层可独立升级、独立排查。

## 三、技术选型对比

### 3.1 向量库

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| **Qdrant** ✅ | Rust 高性能、过滤强、原生支持稀疏+稠密混合、部署轻 | 生态比 Milvus 小 | **推荐**，DGX 单机最合适 |
| Milvus | 功能最全、分布式 | 重，单机杀鸡用牛刀 | 不推荐单机用 |
| Chroma | 极轻、上手快 | 大规模/生产弱、混合检索支持一般 | 仅原型阶段可暂用 |
| pgvector | 复用 PostgreSQL | 稀疏检索、rerank 需自建 | 已有 PG 才考虑 |

### 3.2 Embedding 模型（决定索引精度的第一关键）

| 方案 | 中文能力 | 长文本 | 稀疏+稠密 | 结论 |
|---|---|---|---|---|
| **BGE-M3** ✅ | 强 | 支持（8K） | 原生同时输出稠密+稀疏 | **推荐**，一步到位 |
| BGE-large-zh-v1.5 | 强 | 512 tokens | 仅稠密 | 备选，简单场景 |
| text-embedding-3 | 中 | 一般 | 仅稠密 | 需走 API，不推荐本地 |

> 说明：BGE-M3 一个模型同时产出稠密向量 + 稀疏权重，是「极致向量化」里做混合检索最省事的选型。跑在 DGX 的 GPU 上很快。

### 3.3 重排序 Rerank

- **BGE-reranker-v2-m3**（中文强，与 BGE-M3 同系列，配合好）

### 3.4 接入 OpenClaw 的方式

| 方案 | 说明 | 适用 |
|---|---|---|
| **Skill（推荐）** | 按 OpenClaw skill 规范写一个 second-brain skill，暴露 search/remember 等工具 | 主方案 |
| 独立服务 + Exec 工具 | 检索引擎跑成服务，OpenClaw 用 Exec 调 CLI | 备选/过渡 |
| MCP Server | 若 OpenClaw 支持 MCP 客户端，把引擎做成 MCP server | 视版本而定 |

> 具体 skill 目录结构和规范，动手阶段对照 OpenClaw 官方文档（docs.openclaw.ai）确认，避免版本不兼容。

## 四、「极致向量化」如何落地

1. **多粒度索引（parent-child）**
   - 条文级：一句/一条方证（最细，精准命中）
   - 段落级：一段/一篇的完整上下文（回填原文）
   - 篇章语义摘要级：用千问预先生成每篇的摘要向量，用于"大方向匹配"

2. **混合检索**：稠密（BGE-M3）+ 稀疏（BM25/SPLADE）融合，用 RRF 或加权打分

3. **查询改写与扩展**
   - 中医术语归一：证候、病名、方剂名、药味别名统一（如"失眠"↔"不寐"）
   - Query expansion：检索前用千问把口语问题扩写成多路检索词

4. **Rerank 精排**：召回 Top50 → BGE-reranker 精排 Top5-10

5. **元数据过滤**：来源典籍、朝代、篇目、证候标签、方剂分类，检索时按需过滤

6. **（进阶·可选）领域增强**
   - 用古籍语料对 embedding 做对比学习微调（提升古文/异体字/繁体向量质量）
   - 构建实体图谱：证候 → 病机 → 方剂 → 药味 → 条文，支持多跳检索

## 五、「人脑式思考」如何落地

1. **分层记忆**
   - 工作记忆：当前会话上下文
   - 长期记忆：向量化知识库 + 你的偏好/历史决策
   - 情景记忆：时间线记录（何时做过什么判断、结论是什么）

2. **检索-生成-反思循环（RAG + Self-Reflection）**
   - 检索 → 生成 → 自检（有没有把握、是否缺关键信息）→ 补检索 → 再生成

3. **多跳推理**：证候 → 病机 → 方剂 → 药味加减，链式逐步检索，而不是一次检索到底

4. **记忆自动沉淀**：从对话中抽取可复用知识点，自动写入长期记忆，越用越懂你

## 八、风险提示

- **资源抢占**：27B + embedding + rerank 同机跑，需评估显存/内存峰值，必要时错峰或降精度加载
- **古籍文本质量**：繁体、异体字、OCR 错误会直接拉低索引精度，入库前需做文本清洗
- **OpenClaw 版本兼容**：skill 规范随版本变化，动手时先锁定版本再开发
- **数据隐私**：好消息是全本地运行，数据不出 DGX；但仍需注意 OpenClaw 若接外部渠道（如 Telegram）时只放行必要数据
